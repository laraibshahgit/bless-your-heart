## Scope

This codebase has an unusually small idempotency surface for an audit of this template:

- **No payments, no refunds, no billing operations.**
- **No webhook handlers.** `gh` confirmed: no `webhooks/`, no `callbacks/`, no Stripe/PayPal/Twilio/Shopify integration. The only external signature work is on outbound Anthropic calls.
- **No queue consumers, no background workers, no cron jobs.** The single Netlify function handles requests synchronously and returns.
- **No database of user content.** No INSERT-into-orders, no UPDATE-status patterns. The only Firestore writes are on the rate-limit collection.
- **One state-changing endpoint:** `POST /.netlify/functions/generate`.

The audit therefore narrows to: the generate endpoint, the Firestore rate-limit transaction, the three Anthropic outbound calls, the analytics SDK, and the frontend mutation buttons.

## Duplicate-Execution Analysis

### 1. Generate endpoint — **non-idempotent BY DESIGN, no fix needed**

If a single request body reaches the lambda twice, the second execution will:
- Bump the rate-limit counter twice (correct — each invocation actually does work and bills Anthropic)
- Produce a *different* output, because `temperature: 0.9` and the photo selector excludes prior IDs
- Both responses race back to the client; whichever lands second overwrites poster state

The product *requires* non-determinism: regenerating from the same prompt is a core feature. An idempotency-key pattern (cache response keyed on `prompt + excludePhotoIds`) would defeat the design — users would get the same poster on every retry of a flaky network request.

The duplicate-execution surface is therefore handled at the *trigger* layer (the frontend mutex) rather than at the *endpoint* layer:

- **Generate-button click + form-submit double-fire** — closed by `inFlightRef` mutex (audit run 29/001).
- **Browser-level POST retry on network error** — `fetch` does not auto-retry POST. `callGenerate`'s `AbortSignal.timeout(30s)` only aborts; it never re-fires. Verified.
- **Lambda retry on cold-start failure** — Netlify Functions do NOT retry on user-facing endpoints. (They do for scheduled functions, of which this codebase has none.)
- **User mashing F5 / refresh during loading** — page reload kills the in-flight fetch; no duplicate side effect on the lambda side. The in-flight Anthropic call is wasted but unavoidable.

**Verdict:** Already protected. No further action.

### 2. Firestore rate-limit transaction — **idempotent under concurrency, accepted edge case**

`db.runTransaction(...)` is automatically retried by the Firestore SDK on contention. The transaction body is a pure read-modify-write inside Firestore's serializable isolation, so concurrent calls from different lambda instances cannot double-increment.

**Edge case (already documented):** the transaction is wrapped in a 3-second `Promise.race` timeout in `generate.ts:172`. If the timeout fires while the Firestore write is in flight, the lambda returns `null` rate-result (fail-open path) **but the Firestore write may still complete**. A subsequent request from the same IP would then see an inflated counter for one request that fail-opened. This is *over-strict* behavior, not under-strict — users at the edge of their hourly quota might hit the limit one request earlier than intended. Documented behavior; not a correctness bug.

**Edge case (UTC-salt rotation):** at 00:00 UTC every IP gets a fresh hashed key. A user can do ~25 requests at 23:59:59 UTC and another ~25 at 00:00:01 UTC — effectively 50 requests in a 2-second window. Already documented in CLAUDE.md and [`audit-reports/14_DATETIME_HANDLING_REPORT_001`](14_DATETIME_HANDLING_REPORT_001_2026-05-04_0121.md). Accepted.

**Verdict:** Already idempotent. No further action.

### 3. Anthropic outbound calls — **SDK retries are billing-safe, no idempotency-key support to add**

The Anthropic SDK retries up to 2 times by default on:
- Network errors (request did not reach the API server → not billed)
- 408 Request Timeout (not billed)
- 429 Too Many Requests (rate-limited *before* generation → not billed)
- 500+ Server Errors (not billed)

The Anthropic Messages API as of January 2026 **does not document an `idempotency-key` header**, so passing one would be a no-op. There is no code-level fix here.

The most plausible duplicate-execution scenario — "the request reached Anthropic, generation started, but the network died before the response landed" — would result in the SDK retrying. In that case the original generation may have completed and been billed, and the retry produces a second billable call. This is a known risk for any non-idempotent LLM API. Mitigation: keep the per-request timeout tight (already 12s).

The in-handler retry loop in `generate.ts:251-281` is *not* a duplicate-execution risk — each retry is a deliberately fresh call because the prior attempt was rejected by validation (Zod parse / specificity / tone). Each call produces a different output by design.

**Verdict:** Bounded by per-request timeout + max-retries; no SDK-level fix available.

### 4. Frontend Generate handler — **already protected (audit run 29/001)**

The `<button type="submit">` inside `<form onSubmit>` would otherwise fire React's onClick AND the browser's submit event in the same tick, producing two `callGenerate` calls (~2× Anthropic spend per click) plus a stale-response overwrite race. Audit run 29/001 closed this with:
- `inFlightRef` synchronous mutex (state-derived guards lag a render and don't catch same-tick re-entry)
- `generationIdRef` stale-response token (drops responses from older generations after every `await`)

Verified end-to-end in [`src/App.tsx:85-189`](../src/App.tsx). Pinned by detailed comments at the ref declarations.

**Verdict:** Already protected. No further action.

### 5. Frontend Download button — **already protected**

`handleDownload` synchronously sets `status === 'downloading'`, which sets `disabled` on the button (`DownloadButton.tsx:58`). A second click during the await would land on a disabled button and be ignored.

After download, the post-success window (2.5s `confirmed` state) and post-error window (3s `error` state) DO allow re-clicks — but each click is a fresh download of the same image. This is intentional UX (user might want two copies), not data corruption.

`setTimeout` handles are tracked in a `useRef` and cleared on unmount, so a regenerate-while-toast-is-up cannot leak a `setStatus` onto a dropped component.

**Verdict:** Already protected. No further action.

### 6. PostHog `initAnalytics` — **had a synchronous-re-entrancy gap; FIXED in this run**

#### The bug

```ts
// BEFORE (buggy shape):
let initialized = false;

export function initAnalytics() {
  if (initialized) return;
  if (!import.meta.env.PROD) return;
  if (!import.meta.env.VITE_POSTHOG_KEY) return;

  posthog.init(import.meta.env.VITE_POSTHOG_KEY, {
    // ... config ...
    loaded: () => {
      initialized = true;   // ← set ASYNCHRONOUSLY when posthog finishes loading
    },
  });
}
```

The guard `if (initialized) return` only blocks the second call **after** the asynchronous `loaded` callback fires. Between the synchronous `posthog.init(...)` invocation and the loaded callback completing, there is a window — easily milliseconds, possibly hundreds of ms on slow networks while the PostHog script downloads — during which a re-entrant call to `initAnalytics()` would pass the guard and call `posthog.init()` a SECOND time.

#### Why it matters

`posthog.init()` is **not documented to be idempotent**. Each invocation:
- Constructs a new PostHog instance
- Registers its own pageview listener
- Registers its own `beforeunload` / `pagehide` listeners
- Establishes its own session-storage persistence layer

A duplicate init produces **duplicate pageview captures** for every page-view going forward, plus duplicate session-end events. On any real-world traffic this would inflate analytics by 2x per affected user.

#### Why it is a latent bug today (not a live one)

The only current call site is [`src/main.tsx:15`](../src/main.tsx) — outside the React tree, called exactly once per page load. There is no React effect or callback that could re-enter today.

The bug becomes live the moment a future contributor (perfectly reasonably) moves the call into a `useEffect`:

```ts
useEffect(() => {
  initAnalytics();
}, []);
```

In React StrictMode dev, `useEffect` runs twice on mount. Both runs would call `initAnalytics()` synchronously, both would pass the `if (initialized) return` guard (because `loaded` hasn't fired), and `posthog.init()` would run twice.

#### The fix

```ts
// AFTER (audit run 30/001):
let initialized = false;

export function initAnalytics() {
  if (initialized) return;
  if (!import.meta.env.PROD) return;
  if (!import.meta.env.VITE_POSTHOG_KEY) return;

  // Flip the guard SYNCHRONOUSLY before calling posthog.init.
  initialized = true;

  posthog.init(import.meta.env.VITE_POSTHOG_KEY, {
    // ... config (no `loaded` callback needed) ...
  });
}
```

Same shape as the lazy-init pattern in `getAnthropicClient()` ([`src/server/anthropic.ts:46-51`](../src/server/anthropic.ts)) and `getDb()` (in `firebaseAdmin.ts`).

#### Secondary win

The pre-fix shape also had a quieter bug: events fired *between* `initAnalytics()` and the loaded callback firing were silently dropped by the `if (!initialized) return` guard in `track()`. The very first `track('prompt_submitted')` from a user who clicks Generate immediately on page load could be discarded. Post-fix, `track()` forwards events as soon as `initAnalytics()` returns; PostHog's own client-side queue handles them until the network init completes.

#### Tests

- Existing `is idempotent — second call does not re-init` — **still passes**, but no longer relies on simulating the `loaded` callback.
- New test: `does not double-init when called twice synchronously without simulating posthog load` — pins the bug-fix behavior. Without my fix this test fails (verified locally).

### 7. PostHog `track` calls — **idempotent, fire-and-forget**

All 11 `track()` call sites are guarded by the `initialized` flag. Duplicate `track()` calls would result in duplicate analytics events, which is analytics noise but not a user-visible side effect or data corruption.

The only place a duplicate `track()` could fire for a single user action is `handleRegenerate` ([`src/App.tsx:191`](../src/App.tsx)):

```ts
function handleRegenerate() {
  handleGenerate();    // mutex may bail
  track('regenerate_clicked', ...);   // always fires
}
```

If the user double-clicks Regenerate, the second `handleGenerate()` is bailed by the mutex, but `track('regenerate_clicked')` still fires twice. **However**, the Regenerate button only renders when `state.phase === 'settled'` ([`PosterReveal.tsx:39`](../src/components/PosterReveal.tsx)). The first click synchronously sets `phase: 'loading'`, which unmounts the button before the next render. A user *cannot* physically click it twice in succession — there is no double-fire window. Confirmed safe.

### 8. sessionStorage write (`byh:lastPrompt`) — **inherently idempotent**

`safeSessionSet(SESSION_KEY, value)` is a pure overwrite. Setting the same key twice produces the same final state. Already debounced 300ms with cleanup-on-unmount.

## Operations Classified as "Already Protected"

The following surfaces require **no changes** because their existing protection is correct and complete:

- **Generate-button click** — `inFlightRef` mutex (run 29/001)
- **Form-submit double-fire** — same mutex
- **Network retry on POST** — `fetch` does not auto-retry; `AbortSignal.timeout` only aborts
- **Lambda retry** — Netlify does not retry user-facing functions
- **Firestore rate-limit txn** — `runTransaction` provides serializability
- **Download button double-click** — `disabled={status === 'downloading'}`
- **Anthropic SDK retries** — billing-safe (failed attempts not billed)
- **In-handler retry loop** — each iteration is a deliberately fresh call
- **sessionStorage prompt cache** — pure overwrite
- **`setTimeout` mutations on UI state** — clear-before-set + cleanup-on-unmount (`PromptInput.debounceRef`, `DownloadButton.resetRef`, `PosterCanvas` rAF cleanup)
- **PostHog `track` calls** — fire-and-forget, gated by `initialized`

## Operations Classified as "Accepted Risk, Documented"

- **Rate-limit txn fail-open over-counting** — when the 3s race-timeout fires while the Firestore write is in flight, the user's counter may be incremented for a request that returned with no rate-limit headers. Documented in CLAUDE.md and [`24_DATA_INTEGRITY_REPORT_001`](24_DATA_INTEGRITY_REPORT_001_2026-05-04_1745.md).
- **UTC-salt rotation boundary** — ~25 requests/hour can effectively be 50 across the 00:00 UTC boundary. Documented in [`14_DATETIME_HANDLING_REPORT_001`](14_DATETIME_HANDLING_REPORT_001_2026-05-04_0121.md).
- **Anthropic SDK retries on transport-level failure** — original call may have succeeded server-side and been billed; retry produces second billable call. Industry-standard risk for LLM APIs; no idempotency-key header available on Messages API.

## Conclusion

The codebase has very few state-changing surfaces (no payments, no webhooks, no queues, no DB of user content), and the existing surfaces are well-protected — most by deliberate design choices (the `inFlightRef` mutex from audit run 29/001, the `runTransaction` wrapper for rate-limiting, fail-open patterns with explicit timeouts).

One real bug found: a synchronous-re-entrancy gap in `initAnalytics` that would have caused duplicate PostHog inits the moment any future caller moved the call into a React effect. Fixed with a 1-line flag swap and a regression test.

Net result: zero new known idempotency vulnerabilities, one latent vulnerability closed.
