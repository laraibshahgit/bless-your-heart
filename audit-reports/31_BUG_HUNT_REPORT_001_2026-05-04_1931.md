## High-Priority

### H1. `POSSESSIVE_NAME_PATTERN` regex requires lowercase `my` and lowercase relationship word — capitalized sentences bypass the real-person filter

- **Location**: [`src/server/safety.ts:27-29`](src/server/safety.ts#L27)
- **Confidence**: HIGH (≥95%)
- **Description**:
  ```ts
  const POSSESSIVE_NAME_PATTERN = new RegExp(
    `\\bmy\\s+(${RELATIONSHIP_WORDS.join('|')})\\s+([A-Z][a-z]+)`,
  );
  ```
  No `i` flag. The pattern requires `\bmy` (literally lowercase `my`) and the
  relationship words list is also lowercase (`boss`, `sister`, etc.). Only the
  `[A-Z][a-z]+` group requires capitalization.
- **Impact**: A user who writes "**My** boss Karen is loud" — the most natural
  way to start a sentence — bypasses the real-person filter. The existing test
  at `tests/server/safety.test.ts:24` only covers the lowercase-prefix path,
  and `tests/server/generate-integration.test.ts:134` uses `'my boss Karen'`
  (lowercase). The capitalized variant is unverified.
- **Trigger**: Any prompt where the user capitalizes "My" — likely the majority
  of real-world inputs.
- **Suggested fix**: Make the prefix case-insensitive while keeping the name
  capitalization signal intact:
  ```ts
  const POSSESSIVE_NAME_PATTERN = new RegExp(
    `\\b[Mm]y\\s+(${RELATIONSHIP_WORDS
      .map(w => `[${w[0].toUpperCase()}${w[0]}]${w.slice(1)}`)
      .join('|')})\\s+([A-Z][a-z]+)`
  );
  ```
  (Or pre-lowercase only the `\bmy\s+<word>\s+` portion before regex test, and
  match name on the original.)
- **Why not fixed**: Expanding what the safety filter catches IS a user-facing
  behavior change — prompts that previously passed will now be blocked. Per
  bug-hunt rule, that requires human review (and possibly a corresponding
  copy/voice review for messaging).
- **Test to add**: `expect(checkRealPersonFilter('My boss Linda is loud')).toBe(true);`

## Medium-Priority

### M1. `PosterReveal.canvasReady` is never reset — scroll fires immediately on regenerate, before the new canvas has decoded

- **Location**: [`src/components/PosterReveal.tsx:19-25`](src/components/PosterReveal.tsx#L19)
- **Confidence**: HIGH (≥90%)
- **Description**: `canvasReady` is set to `true` by the FIRST poster's
  `onReady` callback. On regenerate (`settled` → `loading` → `settled`),
  `canvasReady` stays `true` from the previous generation. The
  `scrollIntoView` effect (deps: `[state.phase, canvasReady]`) fires
  immediately on the new `settled` transition because both conditions are
  already met — *before* the new PosterCanvas's image-load + decode + composite
  cycle finishes.
- **Impact**: On regenerate, the page scrolls into the container while the
  canvas is still blank/decoding. Then the canvas appears in place. The
  original design intent ("scroll *after* canvas is ready, not before") is
  silently violated for every regenerate after the first.
- **Trigger**: Click Generate, wait, click Regenerate.
- **Suggested fix**: Add a reset effect when leaving `settled`:
  ```ts
  useEffect(() => {
    if (state.phase !== 'settled') setCanvasReady(false);
  }, [state.phase]);
  ```
- **Why not fixed**: Changes the scroll timing observed by the user (current
  behavior: scroll-then-decode; fixed behavior: decode-then-scroll). User-
  facing visual change.

### M2. `DistressInterstitial` unmounts immediately on close — Radix close animation cannot run

- **Location**: [`src/App.tsx:262-270`](src/App.tsx#L262)
- **Confidence**: MEDIUM (~75%, depends on Radix Dialog version semantics)
- **Description**: The conditional render gate `{distressData.hotline && (...)}`
  drops `DistressInterstitial` from the tree the moment `onClose` fires
  (`setDistressData({ open: false, hotline: null })`). Radix Dialog manages
  its own close-animation lifecycle internally — when the parent unmounts
  the entire `<DistressInterstitial>` synchronously alongside `open=false`,
  there's no time for the fade-out / zoom-out animation defined in
  `dialog.tsx:39`.
- **Impact**: The dialog snap-closes with no transition on the close path.
  Open path still animates because hotline is set BEFORE open=true (one render
  earlier).
- **Trigger**: User clicks "Take me back" or presses Escape while distress
  modal is open.
- **Suggested fix**: Decouple the gate. Keep the dialog mounted with the
  *previous* hotline data until Radix's close animation completes:
  ```tsx
  // Keep hotline state alive; only `open` controls visibility.
  // Reset hotline on a delayed effect or on next-open replacement.
  ```
  Cleanest: move the conditional inside `<Dialog>` so the wrapper persists.
- **Why not fixed**: Visual UX change; requires deciding the lifecycle pattern.

### M3. Fragile substring match for `generation_blocked` analytics reason

- **Location**: [`src/App.tsx:125`](src/App.tsx#L125)
- **Confidence**: HIGH (~95%)
- **Description**:
  ```ts
  track('generation_blocked', {
    reason: result.message.includes('people') ? 'real_person' : 'slur'
  });
  ```
  The dispatcher uses substring `includes('people')` to discriminate between
  the two block reasons. `errorCopy.realPersonBlock` happens to contain
  "people" today; `errorCopy.slurBlock` does not.
- **Impact**: Any future copy edit that removes the word "people" from
  `realPersonBlock` (e.g., switching to "individuals") would silently re-tag
  every real-person block as `slur` in the analytics dashboard. Conversely,
  any `slurBlock` rewording that includes "people" would mis-tag as
  real_person. Pure analytics fidelity issue — does not affect user behavior.
- **Trigger**: Future rewording of either copy string.
- **Suggested fix**: Two viable paths.
  1. *Pin to constants*: `result.message === errorCopy.realPersonBlock
     ? 'real_person' : 'slur'` — exact match on the imported value.
  2. *Server-side discriminator*: extend `GenerateResponse.blocked` with
     a `reason: 'slur' | 'real-person'` field and use that. Cleanest, but
     adds an API field.
- **Why not fixed**: Fix #1 is mechanical but the substring-match is more
  forgiving to future minor copy edits (e.g. a trailing period); the trade-off
  isn't unambiguously better. Fix #2 is the right answer but requires a wire-
  format contract change. Either path is a judgment call.

### M4. `getClientIp` returns empty string when `x-nf-client-connection-ip` header is empty (collapses all anonymous IPs into one rate-limit bucket)

- **Location**: [`src/server/rateLimit.ts:46-52`](src/server/rateLimit.ts#L46)
- **Confidence**: MEDIUM (~75%, depends on Netlify never sending empty header)
- **Description**: `??` (nullish coalescing) treats `''` as a defined value.
  If `headers['x-nf-client-connection-ip'] === ''`, the first branch returns
  `''` — never falls through to `x-forwarded-for` or `'unknown'`. The
  resulting `hashIp('')` collapses all such requests into a single
  rate-limit bucket.
- **Impact**: Latent. Today Netlify reliably sets a real value. A future
  platform change or a pass-through proxy that emits empty headers would
  make every "empty-IP" requester share the same daily quota — they'd all
  be blocked together once 25 of them hit /generate.
- **Trigger**: Netlify or upstream proxy sends `x-nf-client-connection-ip: `.
- **Suggested fix**: Replace `??` with falsy-guard that excludes empty:
  ```ts
  const direct = headers['x-nf-client-connection-ip'];
  if (direct && direct.length > 0) return direct;
  const xff = headers['x-forwarded-for']?.split(',')[0]?.trim();
  if (xff && xff.length > 0) return xff;
  return 'unknown';
  ```
- **Why not fixed**: No evidence Netlify actually sends empty values; defense-
  in-depth tweak.

### M5. `api.ts` synthesizes `retryable: true` on 4xx — overrides server's `retryable: false` for invalid input

- **Location**: [`src/lib/api.ts:25-30`](src/lib/api.ts#L25)
- **Confidence**: MEDIUM (~70%, possibly intentional)
- **Description**:
  ```ts
  if (!response.ok) {
    if (response.status >= 500) return { ..., retryable: true };
    return { ..., retryable: true }; // 4xx also retryable
  }
  ```
  When the server returns 400 (Zod validation fail / malformed JSON), the
  server's response body explicitly has `retryable: false`, but the client
  short-circuits on `!response.ok` and synthesizes a generic message with
  `retryable: true`. The user sees a "Try Again" button on a request that
  the server has marked unretryable.
- **Impact**: User clicks "Try Again", same input is rejected again, sees
  "Try Again" again. Mild loop. Not data-corrupting.
- **Trigger**: Any 400 response (today only fires on Zod fail, malformed
  body, or method-not-allowed).
- **Suggested fix**: Attempt to parse the JSON body for 4xx responses and
  use the server's discriminated response if shape is valid; fall back to
  synthesized message on parse failure.
- **Why not fixed**: The current behavior may be intentional product UX
  ("any client error → try again"), and the user *can* recover by editing
  their input. Requires product judgment.

## Low-Priority / Potential

### L1. `loadImage` setting `img.src = ''` on timeout may produce an unhandled `decode()` rejection in console

- **Location**: [`src/lib/compositor.ts:74`](src/lib/compositor.ts#L74)
- **Confidence**: LOW-MEDIUM (~60%)
- **Description**: When the timeout fires, `img.src = ''` cancels the in-
  flight fetch. The pending `img.decode()` promise then rejects with an
  EncodingError. The race promise has already settled (via the timeout's
  `reject(...)`), so the decode-rejection is unhandled.
- **Impact**: A console warning ("Uncaught (in promise) EncodingError") in
  the rare CDN-stall scenario. No functional break.
- **Suggested fix**: `img.decode().catch(() => {})` to swallow the secondary
  rejection. Or refactor to capture decode promise and chain catch.
- **Why not fixed**: Console noise only; document.

### L2. `analytics.ts` flips `initialized = true` before `posthog.init()` — if init throws, subsequent `track()` calls quietly forward to a non-functional client

- **Location**: [`src/lib/analytics.ts:24-34`](src/lib/analytics.ts#L24)
- **Confidence**: LOW (~50%, posthog-js is generally robust)
- **Description**: Audit run 30/001 deliberately moved the `initialized = true`
  flip to BEFORE `posthog.init(...)` to close a re-entrancy gap (see comment
  in file). The trade-off: if `posthog.init` throws synchronously, `initialized`
  stays `true` and `track()` will pass its guard and call `posthog.capture`
  on a partially-constructed client. posthog-js handles this gracefully in
  practice (events queue, fire on later init), so this is hypothetical.
- **Impact**: None observed today. Could matter if a future PostHog version
  changes its early-error semantics.
- **Suggested fix**: Wrap `posthog.init` in try/catch; reset `initialized = false`
  on throw. But this re-introduces a tiny re-entrancy window — the same one
  30/001 closed. Trade-off.
- **Why not fixed**: Would partially undo run 30/001's fix.

### L3. `PosterCanvas` re-fetches and re-decodes the photo on every window-resize (effect deps include `displaySize`)

- **Location**: [`src/components/PosterCanvas.tsx:47-91`](src/components/PosterCanvas.tsx#L47)
- **Confidence**: HIGH (re: behavior); LOW (re: severity)
- **Description**: The image-load effect runs on `[line1, line2, photoId,
  displaySize]`. When the user resizes the window, `displaySize` changes,
  the effect re-runs end-to-end: new `<img>` element, `img.decode()` call,

- **Impact**: Minor perf. The rAF-throttling in lines 32-44 already coalesces
  resize events to one per frame, bounding the work. No functional break.
- **Suggested fix**: Split into two effects — one for image load (deps:
  `photoId`), one for canvas draw (deps: image, line1, line2, photoId,
  displaySize). Refactor scope.
- **Why not fixed**: Refactor, not bug fix.

## State Machine Analysis

### `PosterPhase` (the state machine in `App.tsx`)

States: `idle`, `loading`, `settled`, `error`. The previously-existing
`revealing` state was removed in audit run 22/001.

Valid transitions actually exercised in `handleGenerate`:
- `idle → loading` (any generate click)
- `loading → settled` (status: ok | safe_fallback)
- `loading → error` (status: error)
- `loading → idle` (status: distress | blocked | rate_limited — see lines
  116, 124, 132 in App.tsx)
- `settled → loading → settled` (regenerate)
- `error → loading → ...` (retry button)
- `settled → error` (canvas-failure callback, see App.tsx:201-208)

**Stuck states**: none. Every state has a path back to `loading` (regenerate
or retry button), which always re-enters the pipeline.

**Concurrent-transition guards**:
- `inFlightRef` mutex blocks reentrant `handleGenerate`. ✓ (audit run 29/001)
- `generationIdRef` token discards stale-response overwrites after every
  `await`. ✓ (audit run 29/001)
- `cancelled` flag in `PosterCanvas` image-load effect blocks setState on
  unmounted component. ✓ (audit run 28/001)

**Observation (M1)**: `canvasReady` in `PosterReveal` is *not* reset on
`phase` transitions away from `settled`, breaking the "scroll only after
canvas ready" contract on subsequent regenerations.

### Rate-limit document state machine (Firestore `rateLimits/{hashedIp}`)

Implicit states: `nonexistent`, `active-window`, `expired-window` (TTL pending),
`blocked-in-window`.

Transitions in `checkAndIncrementRateLimit`:
- `nonexistent → active-window` on first hit
- `active-window → active-window` on count-increment (no TTL slide — pinned
  by `rateLimit-extended.test.ts`)
- `expired-window → active-window` on first hit after windowAge > 1h (TTL
  resets correctly)
- `active-window → blocked-in-window` when count >= limit

**Edge case observed**: at exactly `windowAge === RATE_LIMIT_WINDOW_MS` (1
hour to the millisecond), the strict-`>` test on line 100 keeps the window
"active". The user gets `Math.max(1, …)`-clamped retryAfterSec, retries in 1s,
and the window then resets cleanly. No bug, but the boundary is asymmetric
(strict `>`) — documented for awareness.

## Recommendations

1. **Address H1 deliberately.** The regex case-sensitivity gap is the only
   high-priority finding and the safety-filter is a defense-in-depth layer
   the brand depends on. Pair with a copy/voice review of `realPersonBlock`
   if the expanded coverage produces false positives.
2. **Add an explicit `reason` field to the `blocked` response variant.**
   Closes M3 cleanly *and* removes the latent fragility flagged in run

   fix that restores the design intent.
4. **Document or fix the `Distress` close-animation gap (M2).** The dialog
   is the most sincere component in the product; a snap-close undermines the
   reverence the UX is supposed to convey at that moment.
5. **Consider a CI lint pass for module-level singletons.** Both audit run
   30/001 and L2 (this run) flag patterns where async lazy-init can leak
   into broken state. A custom check (or careful code review) is the only
   automation path until/unless eslint is adopted.
6. **Mirror `tools/lint-photos.ts` rules into the runtime schema test for the
   slur-list / distress-phrases.** Today, modifying those data files only
   trips a test if the tests' mocks reference the same data; the production
   shape is unverified at test time.
