## 1. Executive Summary

This codebase is small, well-tested, and already performance-conscious. There is no traditional database (Firestore is used only for a single-doc rate-limit transaction keyed by hashed IP), no list views, no heavy data transforms. The hot paths that matter are the Netlify function `generate.ts` (cold-start + per-request safety filters + Anthropic SDK calls) and the client-side canvas compositor. Optimization opportunities are bounded; the wins implemented here trim allocations on the safety hot path, eliminate a setTimeout leak, and reduce render-effect churn during window resizes.

## 2. Database Performance

### Inventory
The only persistent store is Firestore, used by **one** path:
- `src/server/rateLimit.ts:checkAndIncrementRateLimit()` — single-document `runTransaction` keyed by `rateLimits/{hashedIp}`.

That transaction does exactly one `tx.get` + one `tx.set` or `tx.update`. There are no joins, no aggregations, no list reads. Every other "data lookup" in the codebase reads from in-memory JSON (`src/data/photos.json`, ~10 entries).

### N+1 queries
None found. There are no loops that issue per-iteration queries. The photo selection algorithm filters an in-memory array.

### Missing indexes
None. The lookup uses the document key (`rateLimits/{hashedIp}`), which is the primary key — no index needed. Composite indexes are not relevant; there are no `where` clauses against multiple fields.

### Other query issues
None.

**Operational note (already documented in CLAUDE.md):** the Firestore TTL policy on `rateLimits.expiresAt` is a project-level setting that the code can't enforce. Any new Firebase environment must have it configured manually, otherwise the collection grows unbounded despite correct write behavior. This is an operational dependency, not a code issue.

| `src/server/safety.ts:6-12` | `checkSlurFilter` called `new RegExp(...)` for every slur on every request | O(n) regex compilations per call where n = list size | Precompiled once at module load into `SLUR_PATTERNS`. | `src/server/validation.ts:111-113` | `contentWords.some(w => line2Tokens.some(lt => stem(lt) === stem(w)))` recomputed `stem(w)` for every `lt` iteration; O(n·m) stems per call | O(n·m) stem ops | Stem each line2 token once into a `Set<string>`; outer pass becomes O(n+m) with O(1) inner lookups |

### Caching Opportunities — Documented

| Data | Strategy | Invalidation | Estimated Impact |
|---|---|---|---|
| `getPhotoById(id)` lookup | Build a `Map<string, Photo>` once at module load instead of `Array.find` per call | Module load is the only invalidation point (photos.json is build-time) | Negligible at current ~10 photos. Worth doing if library grows past ~50. Skipped — premature optimization for current scale (CLAUDE.md "fewer files, less abstraction") |

### Parallelization

Audited the server pipeline; no opportunities for safe parallelization.

- **Slur and real-person filters** could run in parallel, but they're synchronous regex tests that complete in microseconds — `Promise.all` would add overhead, not save time.
- **Distress phrase list and Haiku check** are intentionally sequential (the phrase list is free; Haiku only runs on a miss).
- **Generation + tone check** are sequential by design (tone-check needs the output).

The retry loop is sequential by design — running 3 generations in parallel just to take the first valid one would triple Anthropic spend and isn't justifiable.

### Other Application Findings

- The dynamic `await import('../../src/server/rateLimit')` inside `generate.ts:172` looks like a hot-path import, but it's intentional: it skips loading the rate-limit module entirely when `RATE_LIMIT_PER_HOUR=9999` (local-dev bypass). After the first call on a warm lambda the module is cached. Kept as-is.
- `getAnthropicClient()` already uses lazy module-level memoization — no change needed.

### Potential Issues — Investigated and Not Fixed

- **`fontsReadyPromise` retained at module scope forever** (`src/lib/fonts.ts:3`). This is intentional and correct — fonts are loaded once per page load, the promise must outlive any single component to avoid re-loading. Not a leak.

The hero is above-the-fold on every viewport, so eager loading + high `fetchPriority` is correct. Marginal benefit from converting to `<picture>` element with media queries — left as documentation.
- **`generate.ts:81` uses `Math.floor(Math.random() * arr.length)`** — synchronous, O(1). Fine.

## 6. Optimizations Implemented

All changes preserve behavior — only change performance characteristics.

### `src/server/safety.ts`
**Before**: Every request rebuilt RegExp instances and lowercased the distress phrase list.
**After**: Three module-load arrays (`SLUR_PATTERNS`, `PUBLIC_FIGURE_PATTERNS`, `DISTRESS_PHRASES_LOWER`); per-request work is now pure regex test / substring scan against pre-prepared values.
**Tests**: `tests/server/safety.test.ts` + `safety-extended.test.ts` (30 tests) — all green.

### `src/server/validation.ts`
**Before**: `checkSpecificity` did O(n·m) stem operations per call due to `stem(w)` recomputed inside `.some(lt => stem(lt) === stem(w))`.
**After**: Build a `Set<string>` of stemmed line2 tokens once; outer pass is O(n+m) with O(1) lookups.
**Tests**: `tests/server/validation.test.ts` + `validation-extended.test.ts` + `synonyms.test.ts` (51 tests) — all green.

### `netlify/functions/generate.ts`
**Before**: `setTimeout(..., 3000)` inside `Promise.race` was never cleared when the rate-limit call won. On warm Lambda containers (which pause the event loop between invocations) this leaves a pending timer that fires during the *next* invocation, attempting to reject an already-settled promise.
**After**: Captured the timer handle; `finally` clears it on every exit path. Behavior identical (same 3 s deadline, same fail-open on timeout/error).
**Tests**: `tests/server/generate-rate-limit-integration.test.ts` + `generate-integration.test.ts` + `generate-contract.test.ts` (85 tests) — all green.

### `src/components/PosterCanvas.tsx`
**Before**: Resize handler fired per frame during window drags, each call triggering `setState` → re-render → re-decode photo + redraw canvas.
**After**: rAF-throttled handler — at most one redraw per animation frame; `passive: true`; `cancelAnimationFrame` on unmount.
**Tests**: No direct render test for `PosterCanvas` (the component is canvas-only, no testing-library in this suite). Smoke test + compositor unit tests cover the canvas math.

### `src/components/PromptInput.tsx`
**Before**: Debounce timer for `sessionStorage.setItem` had no cleanup on unmount.
**After**: Added cleanup effect.

### `src/components/DownloadButton.tsx`
**Before**: Two `setTimeout`s (success + error auto-reset) leaked across regen-flow unmounts.
**After**: Stored handle in a `useRef`; cleanup on unmount; new clicks clear the previous timer before queuing a new one.

### `index.html`
**Before**: First Firebase Storage photo fetch paid the full DNS + TCP + TLS handshake after the user clicked Generate.
**After**: Added `<link rel="preconnect" href="https://firebasestorage.googleapis.com" crossorigin>` so the handshake runs during HTML parse.

## 8. Monitoring Recommendations

### Server-side metrics worth tracking
- **Lambda duration p50/p95/p99** — already captured by Netlify. Watch for the p95 climbing past ~6 s (indicates the retry loop is firing or Anthropic is slow).
- **`gen_anthropic_error` event rate** — already logged structured-JSON in `netlify/functions/generate.ts`. Alert if >5% over a 1-hour window.
- **`rate_limit_check_failed` event rate** — fail-open is intentional but a sustained rate indicates Firestore degradation.
- **`gen_safe_fallback` event rate** — a sudden spike means generation is failing; the user-facing UX masks this so you need the metric to know.

### Client-side metrics worth tracking
- **Core Web Vitals**: LCP, INP, CLS. The current LCP candidate is the hero example image (above-the-fold). After adding the Firebase preconnect, watch for an LCP improvement on cold loads — recommend 500 ms shift on slow networks.
- **`canvasWriteFailed` and `download_failed` events** (already logged client-side) — fire-and-forget posthog event would surface canvas-tainting / iOS-quirk issues.
- **Bundle size**: 465 KB JS / 150 KB gzip is acceptable for a single-purpose SPA but should not grow past 200 KB gzip without justification. Consider `vite-bundle-visualizer` (dev-only) when adding new deps.

### Suggested perf testing approach
- Run Lighthouse CI against a deploy preview on every PR with a budget of LCP < 2.5 s (mobile, 4G profile).
- Synthetic monitoring of `/.netlify/functions/generate` p95 latency from a single canary client (e.g. Pingdom-style); alert at >8 s.
- No load testing needed for the rate-limiter (designed for 25 req/hr/IP — you are not going to fall over).
