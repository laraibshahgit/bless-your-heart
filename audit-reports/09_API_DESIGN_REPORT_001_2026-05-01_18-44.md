## 4. HTTP Methods & Status Codes

### Method audit

| Method | Path | Semantic | Verdict |
|---|---|---|---|
| `POST` | `/generate` | Creates a new generation, increments rate-limit counter (Firestore tx). Side effects + non-idempotent (each call returns different content). | ✅ Correct |
| any other | `/generate` | Returns 405 | ✅ Correct |

No GETs that mutate. No POSTs that read. PUT/PATCH/DELETE are not used and don't apply.

### Status code audit

| Code | When | Verdict |
|---|---|---|
| `200` | Every business outcome (ok, blocked, distress, rate_limited, safe_fallback) | Deliberate "wrapper pattern". Internally consistent. |
| `400` | Malformed JSON, Zod validation failure | ✅ Correct |
| `405` | Non-POST method | ✅ Correct, but historically lacked the RFC-required `Allow` header — **fixed** |

### Issues found

**Issue HTTP-1 (FIXED)**: `405` responses violated RFC 7231 §6.5.5 — the spec requires an `Allow` header naming the supported methods. The handler returned `{ statusCode: 405, body: 'Method not allowed' }` with no headers at all.
- **Fix**: 405 now returns `Allow: POST` plus `Content-Type: application/json; charset=utf-8`, with a JSON body matching the standard error shape (`{ status: 'error', message: 'Method not allowed. Use POST.', retryable: false }`).
- **Why safe**: there is no real-world client that sends non-POST to this endpoint and reads the body. The pre-existing contract test even commented "If we ever harmonize, update this assertion" — explicitly inviting this change.

**Issue HTTP-2 (DOCUMENTED, NOT CHANGED)**: `rate_limited` returns HTTP `200` instead of the conventional `429`. This is a **deliberate** wrapper-pattern choice — every JSON outcome uses 200 and the `status` field discriminates. Forcing 429 would break the pattern and require dual-path logic in the SPA. **Recommendation**: keep 200 in v1; if an external (non-SPA) consumer is ever added, introduce a `/api/v2/generate` that uses 429 + `Retry-After` and migrate.

### Fixes applied
- 405 now harmonizes with the rest of the contract (JSON body + `Allow` header).

## 5. Error Response Consistency

### Dominant format

```json
{ "status": "error", "message": "<human-readable>", "retryable": <boolean> }
```

Used by: `400` (validation), `405` (method), and all client-side fallback synthesis in `src/lib/api.ts`. **One canonical shape across the entire surface.**

`blocked`, `rate_limited`, `distress`, `safe_fallback` are not errors — they're business outcomes with their own variants. Correct separation.

### Deviations found

**Issue ERR-1 (FIXED)**: Validation error message was a generic `"Invalid request."` regardless of which field failed. Clients couldn't tell whether `prompt` was missing, too long, or wrong-typed.
- **Fix**: handler now derives a short, consumer-safe message from the first Zod issue: `"Invalid request: prompt is too long."`, `"Invalid request: prompt has the wrong type."`, etc. Names the failing path; never echoes the offending value.
- **Why safe**: the generate-contract test's only assertion was `parsed.message` being truthy — additive improvement, no breakage.

**Issue ERR-2 (FIXED)**: 405 response broke the JSON contract — see HTTP-1 above. Fixed at the same time.

### Error quality assessment

| Criterion | Status |
|---|---|
| Messages helpful and specific | ✅ after fix (path-named); business-outcome messages were already specific (`"Even the universe has a daily limit. Try again in a bit."`) |
| All field errors returned at once | ❌ — fail-fast on first Zod issue. **Recommendation**: not worth changing. The schema has 2 fields; field-by-field is unnecessary and would lengthen the message. |
| Machine-readable error codes | ⚠️ — error responses use only `message` (human-readable). `blocked` distinguishes slur vs real-person via differing message text, not a `reason` enum. **Recommendation**: add an optional `reason` machine code to `blocked` when a non-SPA consumer needs to programmatically distinguish (today the SPA shows the message verbatim, so it's not needed). |
| Sensitive info leaked | ✅ — no SQL errors, stack traces, or internal paths surface. The `tone_check_failed` and `rate_limit_check_failed` events log error strings to server logs only. |

## 8. Misc API Quality

### Rate limiting

| Criterion | Status before | Status after |
|---|---|---|
| Coverage | ✅ — applied on `/generate` | unchanged |
| `X-RateLimit-Limit` header | ❌ | ✅ added |
| `X-RateLimit-Remaining` header | ❌ | ✅ added |
| `X-RateLimit-Reset` header | ❌ | ✅ added |
| `Retry-After` header on denied | ❌ | ✅ added |
| `retryAfterSec` accuracy | ❌ — hardcoded `60` regardless of actual time-to-reset | ✅ computed from `windowStart + 1hr - now`, clamped to ≥1 |

**Issue RL-1 (FIXED)**: The hardcoded `retryAfterSec: 60` in `checkAndIncrementRateLimit()` told blocked users to "try again in 60 seconds", but the rate-limit window is 1 hour. A user who hit the limit would retry every minute and be blocked every minute — a frustrating, misleading loop.
- **Fix**: compute `Math.max(1, Math.ceil((windowEnd - now) / 1000))`. Also returns `resetAt` (epoch seconds at window end) and `limit` so the handler can populate `X-RateLimit-*` headers.

**Issue RL-2 (FIXED)**: No `X-RateLimit-*` or `Retry-After` headers were emitted on any response. Standard convention (see GitHub, Stripe, etc.) is to surface limit state on every rate-limited endpoint so clients can self-throttle.
- **Fix**: handler now threads `rateResult` through to all response paths and emits the four headers wherever the limiter actually ran. On bypass (`RATE_LIMIT_PER_HOUR=9999`) and on fail-open (Firestore stalled), the headers are intentionally absent — the handler doesn't fabricate values.

### Versioning

- No version prefix on the URL today.
- No deprecated endpoints.
- **Recommendation**: keep unversioned until a breaking change is needed. Style guide documents the policy: `/api/v1/<path>` introduced when needed, old path live for 90+ days, `api_v1_call` event logged for visibility.

### Content types

- Response: `Content-Type: application/json; charset=utf-8` on every JSON response. ✅
- Request: handler does NOT verify incoming `Content-Type: application/json`. **Recommendation**: not worth enforcing — `JSON.parse(event.body)` will reject non-JSON anyway with a clear 400. Adding a Content-Type check would only block well-formed JSON sent without the header (some test tooling).

### Idempotency

- The endpoint is **non-idempotent by design**. Each call generates fresh content + increments the rate-limit counter. Idempotency keys would conflict with the product (user would receive the same poster on retry). Correctly omitted.
- **Recommendation**: if a future endpoint is destructive (e.g. account deletion), use the standard `Idempotency-Key` header with `(hashedIp, key)` keyed cache. Documented in the style guide.

### CORS

- No CORS headers emitted. Same-origin only (the SPA hits `/.netlify/functions/generate` from the same domain). Correct for current architecture; if a separate marketing site or third-party integration is ever needed, add explicit `Access-Control-Allow-Origin` with a strict allowlist.

### Discoverability

- No API index endpoint, no HATEOAS links. Not warranted for a single-endpoint product. `docs/API_DESIGN_GUIDE.md` serves as the human-facing reference.
