## 3. Type Safety Improvements Recommended (Not Implemented)

These would be larger or behavior-affecting and were intentionally skipped in this run.

### 3.1 Runtime validation of `GenerateResponse` in `src/lib/api.ts:32`

The client casts `response.json()` to `GenerateResponse` without runtime validation. Because the server uses a Zod-validated schema and we control both endpoints, this is pragmatic — but a regression in the wire format would crash the SPA narrowly. A lightweight runtime guard (just check `typeof body.status === 'string'`) would catch the regression and route to the existing error copy. Not implemented: requires a small refactor of `callGenerate` and would marginally bloat the client bundle if a full Zod schema is mirrored client-side.

### 3.2 Enable `noUncheckedIndexedAccess` in `tsconfig.json`

The strictest TS option not currently on. Would surface ~30 `arr[idx]` accesses as `T | undefined` and force narrowing. Most call sites already check `arr.length > 0` first, so the diff would be largely cosmetic — but a subtle bug class (e.g. `randomPick(arr)` when `arr.length === 0`) would be caught. **Cost:** medium-sized refactor (~20 files); **benefit:** small but real. Worth doing if/when a future change adds new array-access code paths.

### 3.3 Branded types for `photoId`, `hashedIp`

Both are `string` today, easy to mix up at call sites. A branded `PhotoId = string & { __brand: 'PhotoId' }` would prevent passing a hashed IP where a photo ID is expected. **Cost:** low; **benefit:** small (call sites are few and well-isolated).

### 3.4 Tighter env-var typing in `firebaseAdmin.ts`

`cert({ projectId: process.env.FIREBASE_PROJECT_ID, ... })` passes `string | undefined` into a function expecting `string`. The Firebase SDK fails loudly at init-time on missing values, which is acceptable, but explicit `assertEnv('FIREBASE_PROJECT_ID')` helpers would produce better error messages.

## 5. Error Handling Infrastructure Assessment

**What's in good shape:**

- **Server-side fail-open pattern is well-established and tested.** Every `console.error` in `netlify/functions/generate.ts` and `src/server/*` follows the same `JSON.stringify({ event, error: String(err) })` shape, pinned by tests in `tests/server/anthropic.test.ts:189` and `tests/server/safety-extended.test.ts`. The "Fail-open `console.error` log lines MUST include `error: String(err)`" rule is documented in `CLAUDE.md` and was respected throughout this run.
- **React `ErrorBoundary` exists and is wired** at `src/main.tsx:20`. It catches any synchronous render error from the `App` subtree and presents `errorCopy.errorBoundary`.
- **Discriminated union `GenerateResponse`** makes server-side outcome handling explicit at every consumer (App.tsx narrows on `result.status`).
- **Per-request Anthropic SDK timeouts** are enforced everywhere (12 s) — pinned by tests. Without this, a hung provider would burn the full lambda budget.
- **Safe fallback path** — if generation/photo selection both fail, `respondWithSafeFallback` ensures the user never sees a raw error. The retry budget is bounded (2 retries).
- **Origin allowlist (CSRF shield)** in `generate.ts:84` — proper allowlist semantics, not relying on `Referer`.
- **Distress URL/phone sanitization** in `DistressInterstitial.tsx` — `safeTelHref` and `safeHotlineHref` defensively allowlist schemes/characters even though the source is server-controlled. This is exemplary defense-in-depth.

**What was missing (now addressed):**

- Silent client-side catches discarded error context (api/download/validation) — fixed.
- React component async IIFEs (`PosterCanvas`) had no error handling — fixed.
- `sessionStorage` access (`PromptInput`) could trip the ErrorBoundary in incognito iframe contexts — fixed.
- ErrorBoundary log shape inconsistent with server-side convention — fixed.

**What's still missing (recommended, not implemented):**

- **No `window.addEventListener('unhandledrejection', ...)` handler.** Would catch any async rejections that escape the React tree (e.g. analytics SDK failures, `import()` lazy-load rejections). **Recommendation:** add to `main.tsx` and forward to PostHog when initialized; otherwise console.error with the structured shape. Low cost; medium value for production observability.
- **No custom error classes.** All errors are `Error`; the codebase uses string `event` discriminators in logs as a substitute. For this codebase size that's appropriate — no recommendation to add custom classes.
- **No client-side error reporting integration.** PostHog is initialized for analytics events but `disable_session_recording: true`; uncaught errors are not forwarded. If observability of frontend errors becomes important, wire `track('frontend_error', { ... })` from the unhandled-rejection handler and ErrorBoundary.

## 6. Bugs Discovered

### Latent bug 1 — `PosterCanvas` unhandled rejection (medium)

`src/components/PosterCanvas.tsx:33-53` (pre-fix) had an async IIFE with no try/catch. Any rejection (e.g. Firebase Storage 404, photo URL DNS failure) became an unhandled promise rejection. The user-facing symptom was a stuck loading state; the developer-facing symptom was a generic "Uncaught (in promise)" with no breadcrumb to the photo URL.

**Severity:** Medium — happens whenever the photo URL is unreachable. Fired in practice during the migration off the gradient-placeholder photos in run 09.
**Fix:** Wrapped IIFE in try/catch; route to `onFitFailure` and log. The user now gets a clean retry path instead of a hang.
**Behavior preserved:** Cancellation semantics unchanged; the cancellation check before logging means rapid prop changes don't spam the console.

### Latent bug 2 — `PromptInput` sessionStorage in iframe contexts (low)

`sessionStorage.setItem` throws in iframes with third-party cookies blocked (Safari ITP), in private browsing on iOS Safari with quota exhausted, and when `localStorage` is disabled by group policy. The throw would propagate to the React render and trip the ErrorBoundary on the first keystroke — the user would see the "something broke" screen before they had typed anything substantive.

**Severity:** Low — affects a small fraction of users in restrictive browsing contexts.
**Fix:** Extracted `safeSessionGet` / `safeSessionSet` that swallow the throw. Persistence is best-effort; the input keeps working.
**Behavior preserved:** When sessionStorage works, the 300ms-debounced persistence still happens. When it fails, the user just doesn't get prompt restoration on reload.

### Latent bug 3 — `Anthropic.response.content[]` empty-array crash (low)

`response.content[0].type` would throw `Cannot read properties of undefined (reading 'type')` if the SDK ever returned an empty content array. The crash would have been caught by the `try/catch` in both `checkTone` and `checkDistressWithHaiku` and the request would have failed open — so this was *latent* (caught by an outer net) rather than *exposed*. But the catch was meant for SDK errors, not for our own out-of-bounds access.

**Severity:** Low (caught by outer try/catch).
**Fix:** Explicit `const first = response.content[0]; first && first.type === 'text'` narrowing. Empty array is now an explicit code path with a test.

### Not a bug, but worth noting — `rateLimit-extended.test.ts:411-421` already pinned a related case

The "rejects when an existing doc is missing windowStart (corrupt data)" test verifies that the rate-limiter's transaction throws on partially-corrupt docs (so the handler's outer catch fail-opens). My new defensive branch (`exists: true, data: undefined`) is a *different* case (`data` callable, returns undefined) where I chose to **not** throw — instead treating it as a fresh window so the rare race condition doesn't generate a false fail-open log line. This is a behavior change for a 0.0001%-frequency edge case, kept conservative (still allows the request).
